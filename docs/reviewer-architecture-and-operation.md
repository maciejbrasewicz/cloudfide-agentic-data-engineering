# CloudFide — execution, deliverables and reviewer access

## Two layers, one product

**The product is the agentic delivery system**, not a second copy of the sales
ETL. The trusted root contains code that profiles, designs, runs, verifies,
repairs and publishes Data Engineering solutions. It also contains a
pre-existing audited ETL baseline required by its own regression tests and
review tooling.

**The output is a versioned candidate**, written by the real Foundry agents
in a restricted workspace. A reviewed candidate is committed under
`deliveries/run-<GitHub-run-id>/`, along with its generated tests, README,
financial result and a trusted provenance manifest. This is a standalone
Python implementation that executes in a no-network container. It is not an
arbitrary replacement for the platform's `pipeline.py` and `solution.py`.
Replacing those broke established integration imports in PR #28; the
isolated candidate packaging preserved the actual generated bytes while
protecting the platform.

After a human approves the output, integration into a different application
would require a deliberate adaptation/migration with its own tests. This
multiagent example deliberately stops at a draft PR — there is no auto-merge
or silent promotion to root.

## Actual run #44433630928

1. **Data Architect** read the privately provided original specification,
   employer tests, raw source controls and approved policy using seven
   restricted tools. It proposed an implementation contract; it did not
   approve a new business policy.
2. **Data Engineer** wrote actual Python implementation, tests and README.
   Attempt 1 failed: output file absent.
3. The Engineer read the **real sandbox failure** and rebuilt. Attempt 2
   failed: CLI did not implement the required `--input` and `--output`
   arguments.
4. The Engineer repaired the actual CLI defect. Attempt 3 passed the
   independent employer/candidate pytest and original CSV/Decimal oracle.
   The bounded controller selected this candidate and did not attempt a
   fourth iteration.
5. **Verification Engineer**, distinct from the coding role, read the
   original assignment, original test, both implementation files and P3
   evidence. It wrote a new executable pytest. The test passed on the
   candidate and failed on a deliberately broken always-empty function in
   a separate secret-free Docker execution.
6. The publisher verified the actual test, candidate, P3/P4 receipts,
   source hashes and approved output; GitHub initially rejected
   `GITHUB_TOKEN` draft-PR creation. The authorized GitHub connector opened
   [draft PR #28](https://github.com/maciejbrasewicz/cloudfide-agentic-data-engineering/pull/28).
   Its candidate files were packaged under the run-specific path
   unchanged. A separate
   [exact-SHA CI run](https://github.com/maciejbrasewicz/cloudfide-agentic-data-engineering/actions/runs/44478568225)
   passed all 18 original/author/Verifier tests and independent revenue
   reconciliation.

These are **measured results**, not a simulated agent conversation. The
original historical read-only Foundry review remains accessible in a
collapsed archival section, clearly distinct from the real authoring run.

The source documents do not prove the business interpretation of exact
duplicates, negative-quantity returns or historical product-price imputation.
The approved data policy keeps those assumptions visible; automatic tests
cannot validate their economic meaning.

## Reviewer-facing modes

**Public: inspect real work.** Open the single existing CloudFide portal,
choose the execution stage, inspect source file hashes, failure history,
mandatory tools, original run and draft PR. There is no token requirement.

**Public: verify actual output.** Click `Recalculate and verify`. The
server fetches the immutable original `sales.csv` and the published
candidate's five-region output by pinned Git commits. It verifies both
SHA-256 hashes, reconciles original TOTAL before deduplication, independently
cleans the raw source and computes revenue using exact integer cents. It
then compares all five regions to the published output. It executes *new
deterministic calculations now*, not Python, not an LLM, and not an invented
progress animation. If source data or network fail, the button reports
unavailable, not PASSED.

**Protected: execute all three agents.** The operator provisions two
Railway service-only variables: `GITHUB_WORKFLOW_TOKEN` with a fine-grained
GitHub token scoped to this repository and **Actions: Read and write**,
and a strong distinct `REVIEWER_ACCESS_CODE`. Give a code only to an
authorized reviewer. The server dispatches exactly `engineer-e2e.yml` on
`main` with `mode=rebuild`, `max_rounds=3`,
`publish_draft_pr=true`, and a UUID to correlate genuine GitHub job
statuses. The backend enforces a persistent GitHub-run-derived limit of two
workflow_dispatch runs within 24 hours, one active run, plus a local
authentication throttle. No third party can supply source code, change the
task, choose a model, inspect private GitHub credentials or merge a PR.

The repository owner's separate Actions setting **Allow GitHub Actions to
create and approve pull requests** is required for automatic creation of
future draft PRs. The owner reports enabling it on 19 November 2026.
This permission is not evidence that a new automated PR has been tested:
that requires an actual new full Foundry run. The protected launch is
explicitly unconfigured until the Railway variables exist.
